# Historias de usuario y reglas de negocio

Cada historia y cada regla tiene su issue en GitHub con los criterios completos y el contrato de la API. Los criterios de la API se verifican con pruebas de pytest y los de la pantalla se prueban a mano.

## Historias de usuario

| ID | Historia | Criterios | Canal de verificación |
|---|---|---|---|
| HU-01 | Como usuario del sistema, quiero entrar con mi usuario y contraseña, para operar sobre los bienes que me corresponden. ([#4](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/4), [#10](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/10)) | Con usuario y contraseña correctos, `POST /api/auth/login` responde 200 con el token y los datos del usuario y de su unidad.<br>Con un usuario inexistente, una contraseña incorrecta o un usuario inactivo responde 401 con el mismo mensaje.<br>`GET /api/auth/me` devuelve los datos del usuario, y sin token o con un token vencido responde 401.<br>Sin sesión, cualquier página lleva al login.<br>Al entrar se ve el inventario con el usuario y la unidad en el encabezado.<br>Con datos incorrectos se ve "Usuario o contraseña incorrectos".<br>Mientras espera la respuesta, el botón queda deshabilitado.<br>Al recargar la página la sesión sigue iniciada.<br>Si el token vence, vuelve al login. | API y pantalla |
| HU-02 | Como usuario del sistema, quiero cerrar mi sesión, para que nadie use mi cuenta en una computadora compartida. ([#10](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/10)) | Al tocar "Cerrar sesión" vuelve al login y con "atrás" no se puede volver a las páginas protegidas.<br>Si otro usuario inicia sesión en la misma pestaña, no ve datos del anterior. | Pantalla |
| HU-03 | Como Auxiliar Logístico de una Unidad Operacional, quiero ver los bienes de mi unidad y quién los tiene, para saber qué hay en depósito y qué está en dotación. ([#11](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/11)) | Se ven solo los bienes de la unidad, con tipo, identificación, marca, modelo, estado operativo y tenencia: la ubicación si está en depósito, o el legajo y nombre del oficial si está en dotación.<br>Los bienes dados de baja no aparecen.<br>Los bienes con un movimiento pendiente aparecen marcados.<br>Se puede filtrar por tipo de bien.<br>Si la unidad no tiene bienes se ve "No hay bienes para mostrar".<br>Pedir por la API el inventario de otra unidad responde 403. | API y pantalla |
| HU-04 | Como Logístico Regional o de Dirección, quiero ver el inventario de las unidades que dependen de mí, para controlarlas sin pedirles planillas. ([#12](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/12)) | Un usuario de la Regional Norte ve los bienes de la Regional, de A y de B, con una columna de unidad, y no ve los de C.<br>Puede filtrar por una de sus unidades.<br>Un usuario de Dirección ve los bienes de todas las unidades.<br>Pedir el inventario de una unidad fuera del alcance responde 403.<br>`GET /api/unidades` devuelve las unidades que el usuario puede consultar.<br>Un usuario de una Operacional no ve el filtro ni la columna de unidad. | API y pantalla |
| HU-05 | Como usuario de una unidad, quiero registrar la entrega de varios bienes a otra unidad con su acta, para que la unidad de destino la reciba y quede constancia. ([#27](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/27), [#28](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/28)) | Con bienes propios en depósito, de una sola área y sin movimientos pendientes, `POST /api/movimientos/entregas` responde 201 y el acta queda pendiente de recepción.<br>Mientras el acta está pendiente, los bienes siguen en el inventario del origen y aparecen marcados.<br>Un bien que ya está en un acta pendiente o asignado a un oficial responde 409.<br>Un bien de otra unidad responde 403.<br>Armamento y un móvil en la misma entrega responde 422.<br>Un número de acta sin el formato `0001/2026`, una fecha del hecho posterior a hoy o una unidad de destino igual a la propia responde 422.<br>El acta que registra Dirección no queda para revisión.<br>`GET /api/movimientos/{id}` devuelve el acta a las unidades de origen y de destino y a sus superiores.<br>`GET /api/unidades/destinos` devuelve todas las unidades menos la propia.<br>Desde el inventario se eligen varios bienes y "Nueva entrega" abre el formulario con los bienes elegidos.<br>Un bien asignado a un oficial o con un movimiento pendiente no se puede elegir.<br>Si se eligen bienes de dos áreas se ve el aviso de que un acta incluye bienes de una sola área.<br>En el formulario se elige la unidad de destino, se carga el número de acta y la fecha del hecho, que por defecto es hoy, y la descripción es opcional.<br>Al registrarla se ve el acta pendiente y en el inventario sus bienes aparecen marcados.<br>Si otro usuario movió uno de los bienes se ve "Uno de los bienes ya tiene un movimiento pendiente" y el inventario se actualiza.<br>Mientras espera la respuesta, el botón queda deshabilitado. | API y pantalla |
| HU-06 | Como usuario de la unidad de destino, quiero aceptar o rechazar una entrega indicando dónde guardo cada bien, para que el inventario refleje lo que recibí. | `GET /api/movimientos/por-recibir` devuelve a la unidad de destino las actas pendientes con sus bienes.<br>Al aceptar el acta con una ubicación de la unidad para cada bien, `POST /api/movimientos/{id}/recepcion` responde 200, el acta queda aplicada y los bienes pasan al destino en la ubicación indicada.<br>Si falta la ubicación de un bien o es de otra unidad responde 422 y ningún bien cambia.<br>Al rechazarla con un motivo, el acta queda rechazada y los bienes siguen en el origen, en su ubicación y libres para otro movimiento.<br>Un rechazo sin motivo responde 422.<br>Un usuario del origen o de otra unidad responde 403.<br>Un acta ya aceptada o rechazada responde 409.<br>Al aceptarla, cada bien toma un número de orden nuevo y el acta queda pendiente de revisión de la Regional del origen, salvo que la haya registrado Dirección.<br>`GET /api/ubicaciones` devuelve las ubicaciones de la unidad del usuario. | API |
| HU-07 | Como Logístico Regional o de Dirección, quiero revisar los movimientos que registran mis unidades dependientes, para controlarlos y observar los que tienen errores. | Con una entrega aplicada de A a B, `GET /api/revisiones/bandeja` se la muestra a la Regional Norte y no a la Regional Sur ni a Dirección.<br>Una entrega que todavía no se recibió no aparece en la bandeja.<br>Al marcarlo como revisado indicando la versión que vio, `POST /api/movimientos/{id}/revisiones` responde 201, el movimiento queda revisado, se guarda la versión revisada y sale de la bandeja.<br>Al observarlo con un motivo queda observado y sale de la bandeja.<br>Una observación sin motivo responde 422.<br>Si el autor rectificó el movimiento después de que la Regional lo abrió, la revisión con la versión anterior responde 409.<br>Un usuario que no es el superior inmediato de la unidad que registró el movimiento responde 403.<br>Un movimiento ya revisado u observado responde 409.<br>El detalle del acta incluye la lista de revisiones. | API |

## Reglas de negocio

| ID | Regla | Verificación |
|---|---|---|
| RN-01 | Alcance por nivel. Un usuario de una Unidad Operacional consulta solo su unidad, uno de una Unidad Regional consulta su unidad y sus Operacionales, y uno de Dirección consulta todas. Si pide una unidad fuera de su alcance, la API responde 403. | Pruebas de `unidades_visibles` en el [#4](https://github.com/RalbertR/Proyecto_Final_Grupo161/issues/4), una por nivel. Pruebas de la API de HU-03 y HU-04: el 403 fuera del alcance, el inventario por nivel y `GET /api/unidades`. |
| RN-02 | Un acta incluye bienes de una sola área: armamento y chalecos, o móviles y equipos de comunicaciones. Si mezcla las dos, la API responde 422. | Prueba de la API de HU-05 con armamento y un móvil en la misma entrega. |
| RN-03 | Un bien con un movimiento pendiente no admite otro. La API bloquea los bienes con `SELECT ... FOR UPDATE` antes de validar, y el trigger `trg_mb_bien_bloqueado` lo vuelve a controlar en la base. Si el bien ya tiene un movimiento pendiente, la API responde 409. | Pruebas de la API de HU-05: un bien que ya está en un acta pendiente, y dos entregas simultáneas del mismo bien en las que la segunda espera a la primera y responde 409. |
| RN-04 | Mientras la entrega está pendiente, los bienes siguen en la unidad de origen. | Prueba de la API de HU-05 que consulta el inventario del origen después de registrar la entrega. |
| RN-05 | El destino acepta o rechaza el acta completa, una sola vez. La API bloquea los bienes del acta con `SELECT ... FOR UPDATE` antes de leer su estado. Si el acta ya fue recibida, la API responde 409. | Pruebas de la API de HU-06: un acta ya aceptada o rechazada, y dos recepciones simultáneas en las que la segunda espera a la primera y responde 409. |
| RN-06 | Revisa solo el superior inmediato de la unidad que registró el movimiento. Lo que registra Dirección no se revisa. Si otro usuario intenta revisarlo, la API responde 403. | Pruebas de la API de HU-07: la bandeja de la Regional Norte, de la Regional Sur y de Dirección, el 403 para la otra Regional, Dirección y el autor, y el 403 al revisar lo que registró Dirección. |
